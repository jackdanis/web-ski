Golden Ski engine plan

How to refine the engine and add world detail at Snowmass scale while holding 60 fps on a phone. Written 2026-10-22 from a headless profile of main (after PRs #20 to #22). It's a proposal: nothing here is built until you pick.

The game logic is cheap. The two real problems are GPU load (too many triangles, plus every pixel shading four night lamps even at noon) and work that lands in one frame: building tree and rock pages, redrawing and reading back the 1024 px shadow canvas every ~140 m, and re-uploading the whole 8 MB run mask whenever a run tile loads.

2. Detail rings: the rule for everything in the world

Every kind of object gets a version for each distance ring and a line in the budget. New assets, like the TRELLIS buildings, plug into the same rings instead of each bringing its own distance logic.

3. Phases

Phase 1: smooth (no visible change)

  • Work queue. Tree pages, terrain chunks, run meshes and kicker rebuilds go through one queue with a 2 to 3 ms budget per frame, fed ahead of the skier along her velocity, so nothing builds in a single frame.
  • Run mask. Upload only the rows a tile load changes, not the whole 8 MB texture.
  • Shadows. Redraw the shadow canvas in slices over several frames, and drop the full-canvas readback: Goldie's own shade comes from one pixel lookup.
  • Lamps. Compile the four-lamp loop out of the shaders except at night.
  • Lookups. A grid for the 1,700 solid boxes, stations and kickers, so ground and collision checks touch only nearby ones.
  • Lifts. Split the one always-drawn lift mesh per lift so the camera can skip lifts it can't see; only move chairs on lifts within 2.5 km.

Phase 2: triangle budget

  • Add an 8 m run mesh from about 400 m (choice 2). That alone should cut run triangles by about half.
  • A Tab menu readout of triangles, draw calls and frame ms next to the fps, so you can check budgets on your phone.
  • Optional: a pixel density cap or automatic resolution that drops a step when fps falls (choice 3).

Phase 3: load and streaming

  • Move the terrain and run data from base64 inside JS files to binary files. They come out about 25% smaller, skip the JS parse, and can stream.
  • Decode run tiles and build meshes in a Web Worker, handing finished buffers to the page.
  • Bake tree pages offline with the run tiles, so arriving costs a file read instead of hashing every cell.

Phase 4: world detail at scale

  • One props system for signs, poles, fences, kickers and buildings: placed from data files, bucketed by 320 m page, instanced per kind, with ring versions.
  • Buildings from TRELLIS: full model in the near ring, a box with the model's baked colors in mid, gone past 800 m. Repeated buildings share one instanced model.
  • Any new detail (snow texture variation, more buildings, park features) comes with its ring versions and a budget number before it ships.

Phase 5: keep it honest

  • A fixed benchmark route (Elk Camp top to Two Creeks, plus three teleports) that runs headless on every PR and reports triangles, draws, worst frame and load time.
  • The same route on your phone from the Tab menu, with a one-line result you can paste back.

4. Choices

  1. ★ Recommended: Phase 1 first (no visible change), then Phase 2 with the 8 m runs, then the benchmark from Phase 5.
  2. Phase 1 and 2 together in one pass, then decide on the rest.
  3. Phase 1 plus a pixel density cap of 1.5x on phones. Slightly softer, the fastest frame-rate win.

Speeds in this plan are in mph. References I'd like from you for Phase 4: photos of the buildings you want first, and any game whose distant-world look you like (for the mid ring).
